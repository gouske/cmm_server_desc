# 파트 1. 프로젝트 전체 분석 요약

> **프로젝트명**: CMM Server  
> **한 줄 요약**: 여러 명이 동시에 접속해 게임을 즐길 수 있도록 지원하는 멀티플레이어 게임 서버 시스템  
> **영상**: [CBT트레일러](https://youtu.be/4HJIC_365GU?si=unZdBOggZm8_7oyq), [플레이영상1](https://youtu.be/iQbhfPMsVP8?si=v2mMTOKRN2i8ciP9), [플레이영상2](https://youtu.be/p37VRfk0C34?si=nNbjnj7v5uOP53vG)

---

## 어떤 프로젝트인가

추격자와 생존자로 나뉘어 싸우는 멀티플레이어 게임의 서버 시스템입니다.  
로그인부터 매칭, 실제 게임 진행, 결과 저장, 랭킹 집계까지 모든 서버 측 기능을 포함합니다.  
운영 구성 기준 5개의 독립 서버(로비·매칭·게임·랭킹·중계)와 여러 공용 라이브러리로 구성되어 있으며, 개발·테스트·운영 환경을 분리해 관리합니다.  
계정 로그인·토큰 발급은 별도 웹 인증 서버(HTTP)가 담당하고, 게임 서버군은 발급된 토큰을 검증해 사용합니다.

---

## 기술 스택

| 분류 | 기술 | 하는 일 |
|------|------|---------|
| 개발 언어 | C# (.NET Core 3.1) | 서버 프로그램 작성 |
| 공용 라이브러리 | .NET Standard 2.1 | 여러 서버에서 함께 쓰는 코드 묶음 |
| 네트워크 | SuperSocket | 클라이언트 연결 수신·처리 |
| 데이터 전송 형식 | MessagePack | 바이너리 직렬화 기반 패킷 전송 |
| 설정 파일 처리 | Newtonsoft.Json | 설정값을 JSON으로 읽고 쓰기 |
| 로그 | NLog | 서버 상태와 오류를 파일로 기록 |
| 데이터베이스 | MySQL | 유저 계정, 게임 기록 등 영구 저장 |
| 빠른 임시 저장소 | Redis | 접속 중인 유저 정보, 매칭 상태 등 빠른 읽기/쓰기 |
| 보안 | AES-CBC 암호화 | 패킷 내용의 직접 노출과 분석 위험을 낮춤 |
| 클라우드 | AWS (EC2, ELB, ElastiCache, Aurora MySQL) | 운영 환경 인프라 — 서버 구동, 중계 서버 앞단 부하 분산, 관리형 Redis·MySQL 제공 |

## 폴더 구조 한눈에 보기

```
cmm_server/
│
├── SBLibrary/          ← 공용 라이브러리 모음
│   ├── SBCommonLib/    ← 로그, 암호화, 스레드 도구 등 기본 유틸리티
│   ├── SBDatabaseLib/  ← MySQL·Redis 연결 및 쿼리 처리
│   ├── SBSocketServerLib/ ← TCP 서버 틀 (모든 서버가 이걸 기반으로 동작)
│   ├── SBSocketPacketLib/ ← 데이터 묶음(패킷) 포장·해석 도구
│   └── ...
│
├── cmm_common/         ← 서버끼리 주고받는 메시지 형식 정의
│
├── cmm_lobby/          ← 로비·인증 검증·채팅 서버 (포트 4317)
├── cmm_match/          ← 매칭 서버 (포트 4316)
├── cmm_game/           ← 게임 진행 서버 (포트 4315)
├── cmm_rank/           ← 랭킹·시즌 관리 서버 (포트 4319)
├── cmm_bridge/         ← 서버 간 메시지 중계 서버 (포트 4314)
│
├── cmm_server/         ← 통합 서버 원형 (분리 이전 버전, 포트 4320)
│
├── cmm_monitor/        ← 서버 상태 모니터링 화면 (윈도우 앱)
├── DummyClient/        ← 개발용 테스트 클라이언트
└── serverstart.bat     ← 로컬(Windows) 테스트용 일괄 실행 스크립트
```

`serverstart.bat`은 개발 중 로컬 Windows 환경 테스트용 일괄 실행 스크립트로, **bridge → match → rank → game → lobby 5개 프로세스**를 순서대로 실행합니다. 개발 서버(CentOS)와 라이브 서버(Amazon Linux)에서는 별도의 shell script를 작성해 같은 순서로 프로세스를 기동했습니다. `cmm_server`는 서버 분리 이전에 로그인·로비·매칭·게임을 한 프로세스 안의 존(Zone) 스레드로 처리하던 통합 버전으로, 운영 기동 대상이 아닙니다.

---

## 서버별 역할

| 서버 | 맡은 일 |
|------|---------|
| **cmm_lobby** | 클라이언트 관문. 인증 토큰 검증, 유저·캐릭터 데이터 로드, 로비 입장, 친구·클랜 관리, 채팅 |
| **cmm_match** | 게임 대기열 관리, 매치 방 배정 (클라이언트와 직접 통신하지 않음) |
| **cmm_bridge** | 서버 간 메시지 라우팅 및 중계 (중앙 허브) |
| **cmm_game** | 실제 게임 진행, 스킬·맵·보상 처리 |
| **cmm_rank** | 랭킹 점수 계산, 시즌 관리 |
| **cmm_server** | 통합 서버 원형 — 로그인·로비·매칭·게임을 한 프로세스의 존(Zone) 스레드로 처리하던 분리 이전 버전 (운영 미사용) |

계정 로그인과 토큰 발급 자체는 별도 **웹 인증 서버(HTTP)** 가 담당합니다. 게임 서버군(로비·게임)은 클라이언트가 가져온 토큰을 웹 서버에 검증 요청해 확인합니다.

---

## 게임 한 판의 흐름

```
① 유저가 앱 실행
       ↓
② [웹 인증 서버] HTTP 계정 로그인 → 유저 번호·세션 토큰 발급
       ↓
③ [cmm_lobby] TCP 접속 → 토큰 검증, 캐릭터 데이터 로딩, 친구 목록·채팅
       ↓  "게임 찾기" 버튼 클릭
④ [cmm_match] 비슷한 실력의 유저들을 모아 방 구성 (매칭 전용 스레드가 대기열 순회)
       ↓
⑤ [cmm_bridge] 매칭 → 게임 서버의 방 생성 요청을 중계하고,
   게임 서버 주소가 로비를 거쳐 클라이언트에 전달됨
       ↓
⑥ [cmm_game] 클라이언트가 게임 서버에 직접 접속해 게임 진행
   (방이 배정된 게임 스레드에서 상태 갱신)
       ↓  게임 종료
⑦ [cmm_rank] 결과 반영 → 랭킹 점수 업데이트
       ↓
⑧ [Redis] 접속 정보·매칭 상태 빠른 저장
   [MySQL] 게임 기록·계정 정보 영구 저장
```

---

## 데이터 저장 방식

| 저장소 | 용도 | 비유 |
|--------|------|------|
| **MySQL** | 계정, 전적, 통계 등 영구 보존 데이터 | 금고 |
| **Redis (쓰기 전용 연결 풀)** | 접속 세션, 매칭 상태 등 변경 데이터 저장 | 화이트보드 (쓰기) |
| **Redis (읽기 전용 연결 풀)** | 게임 상태 조회, 랭킹 읽기 | 화이트보드 (읽기) |
| **설정 파일** | 서버 주소, 버전, 암호화 키 등 운영 설정 | 운영 매뉴얼 |

# 파트 2. 기술적 하이라이트

---

## 1. Redis 읽기 전용 / 쓰기 전용 연결 분리

**어떤 문제를 해결했나**
데이터를 읽는 요청과 저장하는 요청이 같은 연결을 함께 쓰면, 저장 요청이 많아질 때 읽기 요청도 덩달아 느려지는 병목 현상이 생깁니다.

**어떻게 해결했나**
Redis 연결을 읽기 전용 풀과 쓰기 전용 풀로 완전히 분리했습니다. 두 풀 모두 연결 풀 라이브러리의 LeastLoaded 전략(부하가 가장 적은 연결로 자동 분배)을 적용하고, 연결 오류가 3회 누적되면 자동으로 재연결하는 풀 래퍼를 직접 구현했습니다. 쿼리마다 응답 시간을 측정해 로그로 남기는 진단 기능도 함께 넣었습니다.

**왜 중요한가**
다수 접속 상황에서도 읽기/쓰기 요청 간 간섭을 줄여 응답 지연을 완화할 수 있습니다.

---

## 2. 여러 패킷을 묶어서 한 번에 전송

**어떤 문제를 해결했나**
게임 중에는 아주 짧은 시간 안에 수십~수백 개의 작은 데이터 조각(패킷)이 발생합니다. 이것을 하나씩 따로 보내면 운영체제에 요청을 반복해야 해서 속도가 떨어집니다.

**어떻게 해결했나**
게임 방 단위로 브로드캐스트 패킷을 대기열에 모아 두었다가, 게임 루프 틱마다 최대 1MB 크기의 청크로 병합해 단 한 번의 전송 요청으로 보냅니다.

**왜 중요한가**
전송 대상 유저와 패킷이 많은 방일수록 운영체제 전송 요청 횟수가 크게 줄어듭니다.

---

## 3. 두 개의 작업 목록을 번갈아 사용하는 대기열

**어떤 문제를 해결했나**
새 작업을 추가하는 쪽과 작업을 꺼내 처리하는 쪽이 같은 목록에 동시에 접근하면 서로 기다려야 하는 상황이 생깁니다.

**어떻게 해결했나**
작업 목록을 두 개 만들어 번갈아 사용합니다. 한쪽에 작업을 넣는 동안 반대쪽 목록의 작업을 처리하고, 처리가 끝나면 역할을 바꿉니다. 목록 교체는 잠금 장치 없이 CPU 수준의 원자적 연산(CAS)으로 처리하고, 각 목록 자체는 스레드 안전 큐(ConcurrentQueue)를 사용합니다.

**왜 중요한가**
서로 기다리는 시간을 줄여 게임 서버·매칭 서버 등 메시지가 몰리는 구간에서도 처리 지연을 완화합니다.

---

## 4. CPU 집약 작업과 상태 변경을 분리한 2단계 처리 구조

**어떤 문제를 해결했나**
게임 상태(점수, 위치 등)를 여러 처리 흐름이 동시에 바꾸면 데이터가 꼬일 수 있습니다. 하지만 하나씩 처리하면 CPU 여러 개를 낭비하게 됩니다.

**어떻게 해결했나**
작업을 두 단계로 나눴습니다.
- **1단계**: 여러 백그라운드 스레드가 CPU 집약 작업(패킷 해석 등)을 동시에 처리
- **2단계**: 방(룸)이 배정된 게임 로직 스레드 하나만 그 방의 상태를 변경 — 게임 로직 스레드는 복수 개를 두고 방을 분배하되, 한 방은 항상 같은 스레드에서만 처리되도록 보장

**왜 중요한가**
CPU 성능을 활용하면서도 방 단위 상태 변경 경로를 단일화해 데이터 일관성을 유지합니다. 게임 서버에 적합한 동시 처리 구조입니다.

---

## 5. 실행 시각 기준으로 정렬되는 작업 예약 자료구조 구현

**어떤 문제를 해결했나**
예약된 작업을 실행 시각 순서대로 꺼내려면, 작업 수가 늘어도 꺼내는 비용이 급격히 커지지 않는 자료구조가 필요합니다. 당시 사용하던 .NET Core 3.1에는 표준 우선순위 큐가 없었습니다.

**어떻게 해결했나**
실행 시각 기준으로 정렬되는 우선순위 목록(최소 힙)을 직접 구현했습니다. 가장 빨리 실행해야 할 작업을 O(log N)의 시간 복잡도로 넣고 꺼낼 수 있고, 아직 실행 시각이 안 된 작업에 도달하면 즉시 순회를 멈춥니다.

**왜 중요한가**
시간 기반 예약 작업을 효율적으로 처리할 수 있는 기반 자료구조를 표준 라이브러리 없이 직접 설계·구현한 경험입니다.

---

## 6. 필요할 때만 정리하는 수신 버퍼 (서버 간 통신 채널)

**어떤 문제를 해결했나**
데이터를 받을 때마다 메모리를 새로 할당하면 메모리 쓰레기 수집(GC)이 자주 발생해 성능이 저하됩니다.

**어떻게 해결했나**
서버끼리 통신하는 채널의 수신 경로에 고정 크기 버퍼를 두고, 읽은 위치와 쓴 위치를 별도로 관리합니다. 데이터를 읽을 때는 복사하지 않고 "시작~끝" 위치(ArraySegment)만 알려줍니다. 버퍼가 꽉 찰 때만 한 번에 정리합니다. (클라이언트 세션의 수신은 SuperSocket 프레임워크의 수신 파이프라인이 담당합니다.)

**왜 중요한가**
서버 간 채널은 모든 유저의 메시지가 지나다니는 길목이므로, 이 경로의 불필요한 할당과 복사를 줄이는 효과가 큽니다.

---

## 7. 잠금 없이 상태를 바꾸는 원자적 제어

**어떤 문제를 해결했나**
여러 스레드가 동시에 같은 값을 바꾸려 할 때 잠금(lock)을 걸면, 기다리는 스레드가 쌓여 성능이 저하됩니다.

**어떻게 해결했나**
CPU 명령어 수준에서 지원하는 비교-교체(Compare-And-Swap) 연산을 활용했습니다. "현재 값이 0이면 1로 바꿔라"를 잠금 없이 원자적으로 처리합니다. 이중 대기열의 버퍼 교체 등 패킷 처리 경로의 상태 전환에 적용했습니다.

**왜 중요한가**
모든 패킷이 통과하는 핵심 경로의 상태 전환에서 잠금을 제거해 잠금 경합을 줄였습니다.

---

## 8. 실력 등급별 매칭 + 파티원 동일 방 배정

**어떤 문제를 해결했나**
실력 차이가 큰 유저가 같은 게임에 배정되거나, 함께 게임 찾기를 한 파티원이 다른 방으로 분리되는 문제가 있을 수 있습니다. 또 매칭이 오래 걸리는 유저는 조건을 고집하기보다 게임을 빨리 잡아주는 것이 낫습니다.

**어떻게 해결했나**
사전 생성해 둔 매치 방 풀에서 방을 재사용하고, 방마다 허용 등급 범위(상한·하한)를 두어 입장 가능 여부를 검사합니다. 방이 정원을 못 채운 채 대기 시간이 길어지면 등급 범위를 단계적으로(3단계) 넓혀 매칭 성사율을 높입니다. 듀오 파티는 두 명을 반드시 같은 방에 함께 배정합니다. 매칭 전용 스레드가 짧은 주기로 대기열을 순회하며 유저를 일괄 배정합니다.

**왜 중요한가**
실력 기반의 공정한 매칭과 대기 시간 사이의 균형을 맞추고, 파티원이 같은 방에 배정되도록 했습니다.

---

## 9. 중앙 메시지 라우터 (Bridge 서버)

**어떤 문제를 해결했나**
여러 서버가 서로 직접 연결되면 연결 수가 기하급수적으로 늘어나고, 서버 주소가 바뀔 때마다 여러 곳의 설정을 수정해야 합니다.

**어떻게 해결했나**
Bridge 서버를 중앙 허브로 두고 모든 서버 간 메시지를 여기서 중계합니다. 각 서버는 기동 시 Bridge에 자신의 종류를 등록하고, Bridge는 서버 종류 기반 라우팅 테이블로 패킷을 대상 서버에 전달합니다. 각 서버는 환경별(dev/test/live)로 분리된 Bridge 주소만 알면 다른 서버와 통신할 수 있습니다.

**왜 중요한가**
서버 간 직접 연결(N:N)을 제거해 결합도를 낮추고, 서버 주소가 바뀌어도 각 서버는 Bridge 주소 하나만 관리하면 되도록 통신 경로를 단순화했습니다.

---

## 10. 클라이언트-서버 패킷 암호화 (AES-CBC)

**어떤 문제를 해결했나**
데이터를 암호화하지 않으면 네트워크를 가로채 게임 패킷을 분석하거나 변조하는 치트 도구를 만들 수 있습니다.

**어떻게 해결했나**
클라이언트와 서버 사이의 패킷 본문을 직렬화 단계에서 기본값으로 AES-CBC 방식으로 암호화합니다. 블록이 반복되면 패턴이 보이는 ECB 방식은 피하고 CBC 방식을 선택했습니다.

**왜 중요한가**
패킷을 가로채더라도 내용을 직접 확인하기 어렵게 하고, CBC 방식 선택으로 반복 패턴 노출 위험을 낮추었습니다. (키 관리는 설정 파일 기반으로 단순하게 운영했고, 환경별 키 분리·시크릿 관리 도입은 개선 과제로 남았습니다.)

# 파트 3. 경력 기술서 — 핵심 업무 및 성과

> **프로젝트**: 멀티플레이어 게임 서버 시스템  
> **기술 스택**: C# · .NET Core 3.1 · SuperSocket · MessagePack · MySQL · Redis · AWS  
> **역할**: 서버 엔진 설계 및 구현, 공용 라이브러리 개발, 게임 서버 시스템 구축  

---

## 1. 네트워크 전송 성능 개선

### 1-1. 패킷 묶음 전송 시스템 설계 및 구현

**[상황]** 게임 특성상 짧은 시간 안에 수십~수백 개의 작은 데이터 조각이 발생하는데, 이를 하나씩 따로 전송하면 운영체제에 요청이 반복되어 전체적인 응답 속도가 느려지는 문제가 예상됐다.

**[행동]** 게임 방 단위로 브로드캐스트 패킷을 스레드 안전 대기열에 모아 두었다가, 게임 루프 틱마다 최대 1MB 크기의 청크 버퍼에 병합해 한 번의 전송 요청으로 보내는 방식을 구현했다.

**[결과]** 같은 방에서 여러 이벤트가 발생해도 유저당 전송 요청이 틱당 1회로 묶여 운영체제 전송 요청 횟수를 줄이고 네트워크 처리 부하를 감소시켰다.

---

### 1-2. 서버 간 통신 수신 버퍼 최적화

**[행동]** 서버끼리 통신하는 채널의 수신 경로에서 메모리를 새로 할당하지 않고 고정 크기 버퍼를 재사용하는 방식으로 구현했다. 읽은 위치와 쓴 위치를 별도로 관리해 데이터를 읽을 때 복사가 발생하지 않도록 ArraySegment로 처리했다. 버퍼가 가득 찰 때만 한 번에 정리하는 방식으로 불필요한 처리를 최소화했다.

**[결과]** 서버 간 메시지가 모두 지나는 중계 경로의 메모리 할당과 복사를 줄여 가비지 수집 부담을 감소시켰다.

---

### 1-3. 클라이언트-서버 패킷 암호화 구현

**[상황]** 클라이언트와 서버 사이의 통신 데이터가 암호화되지 않으면 외부에서 이를 가로채 치트 도구 제작에 활용할 수 있는 보안 위협이 존재했다.

**[행동]** 패킷 본문을 직렬화 단계에서 기본값으로 AES-CBC 방식으로 암호화하도록 구현했다. 블록이 반복되면 패턴이 드러나는 취약한 방식(ECB)을 피하고, 반복 패턴 노출 위험이 낮은 CBC 방식을 선택했다.

**[결과]** 클라이언트-서버 간 패킷 데이터를 암호화해 외부 도구를 통한 패킷 내용 분석과 노출 위험을 낮추었다. 다만 키 관리는 설정 파일 기반의 단순한 구조였고, 환경별 키 분리와 시크릿 관리 도구 도입은 당시 적용하지 못한 개선 과제로 남았다.

---

## 2. 동시 처리 성능 최적화

### 2-1. CAS 기반 이중 대기열 구현

**[상황]** 서버의 핵심 메시지 처리 경로에서 새 작업을 넣는 쪽과 작업을 꺼내 처리하는 쪽이 같은 목록을 동시에 접근하면 서로 기다려야 하는 병목이 발생할 수 있었다.

**[행동]** 두 개의 작업 목록을 번갈아 사용하는 방식을 설계했다. 한쪽에 작업을 추가하는 동안 나머지 한쪽의 작업을 처리하고, 완료되면 역할을 교체한다. 역할 교체는 CPU 수준의 원자적 연산(CAS)으로 잠금 없이 처리하고, 각 목록 자체는 스레드 안전 큐를 사용해 안정성을 확보했다.

**[결과]** 대기열 교체 시점에 잠금 대기 없이 빠르게 전환할 수 있어, 게임 서버와 매칭 서버의 패킷 처리 경로에서 메시지가 몰리는 구간의 처리 성능을 안정적으로 유지했다.

---

### 2-2. 무거운 작업과 상태 변경을 분리한 2단계 처리 구조

**[상황]** 게임 상태(점수, 플레이어 위치 등)를 여러 처리 흐름이 동시에 바꾸면 데이터가 꼬일 수 있다. 반면 하나씩 순서대로 처리하면 여러 CPU 코어를 놀리게 되는 비효율이 생긴다.

**[행동]** 작업을 두 단계로 명확히 분리했다. 1단계에서는 여러 백그라운드 스레드가 데이터 해석 등 무거운 작업을 동시에 처리하고, 2단계에서는 방(룸)이 배정된 게임 로직 스레드 하나만 해당 방의 상태 변경을 순서대로 처리하는 파이프라인 구조를 설계했다. 게임 로직 스레드는 설정에 따라 복수 개를 두고 새 방을 부하가 가장 적은 스레드에 배정하되, 한 방의 상태는 항상 같은 스레드에서만 변경되도록 보장했다.

**[결과]** CPU 코어를 활용하면서도 방 단위 상태 변경 경로를 단일화해 데이터 일관성을 유지하는 구조를 구성했다. 이 구조의 핵심 큐 구현을 공용 라이브러리로 분리해 게임 서버와 매칭 서버의 패킷 처리 스레드에 적용했다.

---

### 2-3. 실행 시각 정렬 우선순위 자료구조 구현

**[상황]** 예약된 작업을 실행 시각 순서로 처리하려면 효율적인 정렬 자료구조가 필요했는데, 당시 사용하던 .NET Core 3.1에는 표준 우선순위 큐 자료구조가 없었다.

**[행동]** 실행 시각을 기준으로 자동 정렬되는 우선순위 목록(최소 힙) 자료구조와 이를 이용한 작업 예약 타이머를 공용 라이브러리에 직접 구현했다. 다음 실행 시각 확인은 추가 연산 없이 가능하고, 작업 등록·꺼내기는 목록 크기의 로그 비례 시간(O(log N)) 안에 처리된다. 현재 시각보다 미래인 작업에 도달하면 즉시 처리를 멈춰 불필요한 순회를 제거했다.

**[결과]** 시간 기반 예약 작업을 작업 수 증가에도 안정적으로 처리할 수 있는 기반 자료구조를 표준 라이브러리 없이 직접 설계·구현했다.

---

## 3. 데이터 인프라 설계

### 3-1. Redis 읽기/쓰기 연결 분리 및 자동 복구 구현

**[상황]** 게임 서버에서 세션 관리, 매칭 상태 등 다양한 용도로 Redis를 사용하면서 읽기와 쓰기 요청이 같은 연결 묶음을 공유해 쓰기가 많아질 때 읽기 속도가 저하될 수 있었다.

**[행동]** 읽기 전용 연결 묶음과 쓰기 전용 연결 묶음을 완전히 분리해 운영했다. 두 풀 모두 연결 풀 라이브러리의 LeastLoaded 전략(부하가 가장 적은 연결로 자동 분배)을 적용하고, 연결 오류가 3회 누적되면 자동으로 재연결하는 풀 래퍼를 직접 구현했다. 쿼리별 응답 시간을 측정해 로그로 남기는 진단 기능도 포함했다.

**[결과]** 읽기와 쓰기 트래픽을 분리해 서로 영향을 주지 않는 구조를 완성했다. AWS ElastiCache 운영 환경에서 일시적 네트워크 이상이 발생해도 자동 재연결로 서비스 영향을 줄일 수 있도록 구성했다.

---

## 4. 서버 아키텍처 설계

### 4-1. 역할별 독립 서버 구조 설계

**[행동]** 하나의 큰 서버 대신 로비·매칭·게임·랭킹·중계의 5개 독립 서버로 기능을 나눈 구조를 설계·구현했다. 계정 로그인·토큰 발급은 별도 웹 인증 서버(HTTP)와 연동하고, 게임 서버군은 토큰 검증만 담당하도록 인증 책임을 분리했다. 공통으로 사용하는 네트워크 처리 기반 코드를 라이브러리로 분리해 모든 서버가 동일한 기반 위에서 동작하도록 표준화했다. 설정 파일 변경을 감지해(FileSystemWatcher) 서버를 재시작하지 않고도 일부 설정이 즉시 반영되는 구조를 적용했다.

**[결과]** 서버별 독립 배포 및 규모 확장이 가능한 구조를 확립했다. 공용 라이브러리 분리로 새 서버를 추가할 때 반복 작업이 최소화됐다. 일부 운영 설정 변경 시 서버 재시작 부담을 줄일 수 있도록 구성했다.

---

### 4-2. 서버 간 중앙 메시지 중계 서버 구현

**[상황]** 서버가 여러 개로 분리되면서 각 서버가 서로 직접 연결되면 연결 수가 기하급수적으로 늘어나고, 한 서버의 주소가 바뀔 때 여러 곳의 설정을 수정해야 하는 관리 문제가 예상됐다.

**[행동]** Bridge 서버를 중앙 허브로 설계해 모든 서버 간 메시지를 이곳에서 중계했다. 각 서버가 기동 시 자신의 종류를 Bridge에 등록하면, Bridge가 서버 종류 기반 라우팅 테이블과 메시지 종류(PacketId)에 따라 올바른 대상 서버로 전달한다. 1:1 전달, 1:다수 전체 전달 등 다양한 전달 패턴을 모두 처리한다.

**[결과]** 서버 간 직접 연결(N:N)을 제거해 각 서버는 Bridge 주소 하나만 알면 다른 모든 서버와 통신할 수 있게 됐다. 서버 주소 변경 시 영향 범위를 줄이고 서버 간 결합도를 낮췄다.

---

### 4-3. 등급 기반 매칭 시스템 구현

**[행동]** 사전 생성한 매치 방 풀을 재사용하고, 방마다 허용 등급 범위(상한·하한)를 두어 입장 가능 여부를 검사하는 매칭 구조를 설계했다. 대기 시간이 길어지면 등급 범위를 단계적으로(3단계) 넓혀 매칭 성사율을 높였다. 2인 파티는 두 명이 반드시 같은 방에 배정되도록 별도로 처리했다. 여러 처리 흐름이 동시에 접근해도 충돌이 없는 자료구조를 사용하고, 매칭 전용 스레드가 짧은 주기로 대기 유저를 일괄 배정한다.

**[결과]** 비슷한 실력끼리 매칭하면서도 대기 시간이 과도하게 길어지지 않는 구조를 구현하고, 파티원이 같은 방에 배정되도록 구성했다. 동접 유저 증가 상황에서도 매칭 처리 병목을 줄이고 확장 가능성을 높였다.

### 4-4. 시즌 랭킹 시스템 구현

**[행동]** 현재 시즌과 지난 시즌 랭킹 데이터를 함께 관리하는 구조를 설계했다. 날짜를 기준으로 시즌 전환을 자동으로 감지하고 처리한다. 시즌 랭킹 집계와 기록 저장은 MySQL을 기반으로 처리하도록 구현했다.

**[결과]** 시즌 전환 시에도 랭킹 데이터 갱신과 지난 시즌 기록 조회가 이어지도록 구성했다. 게임 결과가 랭킹에 반영되는 처리 흐름을 완성했다.
